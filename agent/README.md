# TileLang Operator Development Agent Installation and Usage Guide

This directory provides the end-to-end TileLang operator development entry point for Ascend NPUs. It covers hardware identification, solution design, code generation, accuracy validation for specified cases, system testing (ST), user-confirmed performance tuning, and user-confirmed final code review. The runtime configurations under `.codex/`, `.opencode/`, and `.claude/` are all generated by the installer; do not maintain three separate copies of the workflow content. `core/` is the sole source of truth for agent and workflow definitions, and the shared skill sources are under `../.agents/skills/tilelang-ascend-op/`.

## Installation

The target tool must be selected explicitly. Pass `--tool` repeatedly to install for multiple tools at once.

By default, a project-scope installation targets the `agent/` directory containing `init.sh`, regardless of the current directory from which the command is run. This directory is the isolated entry point for the end-to-end TileLang operator development workflow.

```bash
bash agent/init.sh --tool codex --scope project
bash agent/init.sh --tool opencode --scope project
bash agent/init.sh --tool claude --scope project
bash agent/init.sh --tool codex --tool opencode --tool claude --scope project
```

By default, OpenCode selects the permission schema based on the locally installed CLI major version: 1.x uses `classic`, while 2.x uses `v2`. If the OpenCode CLI is not installed, the installer generates the current stable `classic` schema by default. To pregenerate configuration for another environment, specify the schema explicitly:

```bash
bash agent/init.sh --tool opencode --scope project --opencode-schema classic
bash agent/init.sh --tool opencode --scope project --opencode-schema v2
```

Install into another project's dedicated `agent/` directory:

```bash
bash agent/init.sh --tool opencode --scope project --path /path/to/project/agent
```

Install globally:

```bash
bash agent/init.sh --tool claude --scope global
```

## Safety and Validation

```bash
bash agent/init.sh --all-tools --scope project --dry-run
bash agent/init.sh --check
bash agent/init.sh --tool codex --scope project --check
bash agent/init.sh --tool opencode --scope project --uninstall
```

When used without `--tool`, `--check` statically validates the source package's manifest, references, skills, and adapters. When a `--tool` is specified, it also checks that the corresponding installation manifest and generated files are complete and current.

The installer manages only files registered in `tilelang-tuning-manifest.json`. Installation stops if the target location contains an unmanaged file with the same name. Use `--backup-existing` to back it up before installation, or explicitly use `--force` to overwrite regular files and symbolic links. `--force` never deletes real directories.

## Launch

- First enter the dedicated directory: `cd agent`
- Codex: `codex`
- OpenCode: `opencode .`
- Claude Code: `claude`

A project installation generates a short `AGENTS.md` under `agent/`, allowing Codex and OpenCode to enter the complete TileLang operator development workflow automatically and load their installed `tilelang-tuning` agent during the performance-tuning stage. Claude Code imports the same entry point through `CLAUDE.md` in that directory. `core/` remains the sole source of truth for agent and workflow definitions; the installer does not copy the full text into entry-point files.

When Codex, OpenCode, or Claude Code is launched from the repository root, it does not load the entry instructions under `agent/`, so ordinary development sessions remain unaffected. When launched from `agent/`, operator design, implementation, testing, and tuning artifacts are written to `agent/operators/` as specified by the workflow.

A global installation has no fixed project entry point and does not activate the end-to-end operator workflow automatically. In this case, explicitly select the `tilelang-tuning` agent for performance tuning or name the required skill to run an individual stage. A global installation does not create `AGENTS.md` or `CLAUDE.md` in the user's home directory.

## Quick Start

### Start an End-to-End Delivery from an Operator Requirement

After launching the tool from `agent/`, simply state which operator to implement. For example:

```text
Please implement a TileLang RMSNorm operator and follow the complete Design, Generation, Test, Tuning, and Review workflow.
```

If required information such as operator semantics, inputs and outputs, dtype, target backend, or specified accuracy cases is missing, the agent asks for it at the appropriate stage. After ST, the agent asks whether to continue with performance tuning. After tuning, it asks again whether to perform the final code review.

### Start Directly with Performance Tuning

If the operator and its accuracy tests already exist, you can enter `tilelang-tuning` directly. To prevent generation, accuracy-validation, or ST cases from being treated as performance cases by default, explicitly provide or confirm every performance case:

```text
Please tune the performance of the rms_norm operator.

Mode: Flash
Backend: PTO
Code directory: /path/to/rms_norm
Operator file: rms_norm.py
Accuracy test: test_rms_norm.py
Performance cases:
1. M=1, N=4096, dtype=float16
2. M=32, N=4096, dtype=float16
Performance target: improve every case over the current baseline with no per-case regression.
```

Tuning supports two modes. `Flash` uses a single agent for lightweight, rapid, autonomous iteration. `Standard` follows the complete process for initial accuracy validation, profiling every case, solution design, independent implementation comparison, final regression, and evidence archiving. If the prompt does not specify a mode or backend, the agent asks for them in two separate rounds and does not choose a default.

## Main Workflow

An end-to-end delivery has five stages:

> Design → Generation → Test → Tuning → Review

The following boundaries apply to each stage:

- The Design stage identifies the target hardware before producing an implementation plan. If required information is missing, it pauses and asks the user for the missing details.
- The Generation stage implements the operator and passes accuracy validation for the specified cases.
- The Test stage performs system testing (ST) and expands generalized-case coverage. It must obtain explicit user confirmation after ST before entering the Tuning stage.
- Cases from generation, accuracy validation, or ST are not performance cases by default. The user must explicitly provide or confirm the performance cases.
- After the Tuning stage is complete, the workflow must obtain explicit user confirmation again before entering the Review stage.
- The Review stage examines only the final delivery code. It must obtain explicit user approval before fixing any issues.
- The complete workflow targets NPUs only and excludes CUDA, Metal, and other backends.

## Invoke a Skill Independently

If you need only one stage, name the corresponding skill directly in the prompt. An independent invocation performs only that skill's responsibilities and does not automatically continue through the complete workflow.

| Skill | When to use it | Primary boundaries or outputs |
| --- | --- | --- |
| `npu-arch` | Detect the Ascend NPU model, architecture generation, resource specifications, and supported features | Produces `full_soc`, `npu_arch`, and complete hardware evidence; this workflow accepts only the Ascend 950 (A5) target platform |
| `tilelang-op-design` | Create a new design from operator requirements, migrate a design, or revise an existing design | Generates or updates `design.md`; does not implement code, expand generalized tests, or tune performance |
| `tilelang-op-generate` | Generate a TileLang operator from the requirements and `design.md` | Generates one kernel per public computation entry and delivers exactly two Python files, the kernel and its pytest; guarantees accuracy only for the specified cases and does not perform ST or performance tuning |
| `tilelang-op-test` | Create, supplement, or accept system tests | Covers functionality, accuracy, boundaries, gradients, state mutation, invalid inputs, layouts, interfaces, backend paths, and other applicable areas; ST cases do not automatically become performance cases |
| `tilelang-op-profiling` | Collect NPU performance data and identify bottlenecks | Handles on-device profiling, data archiving, and bottleneck evidence; does not replace the complete tuning workflow |
| `tilelang-perf-optimize` | Design performance-optimization plans from PTO profiling evidence | Produces up to three verifiable, reversible plans; does not modify operator code directly or handle ordinary functional failures |
| `tilelang-performance-best-practices` | Consult TileLang Ascend/PTO implementation patterns during generation, migration, review, or tuning | Provides references for APIs, tiling, pipelines, memory hierarchy, and representative host + kernel implementations; reference code must still be checked against the current framework source |
| `tilelang-op-review` | Perform a pre-submit review of TileLang, Python, and Markdown deliverables | Checks formatting, correctness, safety, and verifiable performance; reports issues first and does not modify source without explicit approval |

For example, to generate only the design document:

```text
Use tilelang-op-design to generate design.md from the following operator requirements: ...
```

To perform only a pre-delivery review:

```text
Use tilelang-op-review to review operators/rms_norm/rms_norm.py and test_rms_norm.py. Report the findings first and do not modify the files.
```

The entry point for complete performance tuning is the `tilelang-tuning` agent, not the standalone `tilelang-perf-optimize` skill. The latter is responsible only for producing optimization plans.

## Directory Responsibilities

- `core/agents/`: platform-independent agent definitions.
- `core/workflows/`: platform-independent workflows and fixed task templates.
- `adapters/`: runtime-format templates for Codex, OpenCode, and Claude Code.
- `../.agents/skills/tilelang-ascend-op/`: shared TileLang Ascend skill sources referenced by the installation manifest.
- `manifest.json`: agent names, roles, subagent relationships, workflows, and the skill inventory.
- `scripts/install.py`: configuration rendering, installation, validation, and uninstallation logic.
- `init.sh`: the unified command-line entry point for the installer.
- `operators/`: operator design, implementation, testing, and tuning artifacts produced by workflows launched from this directory.

The repository's existing `tests/` directory remains unchanged. This installer does not add a separate Python test directory; the `--check` commands described above provide its validation capabilities.
