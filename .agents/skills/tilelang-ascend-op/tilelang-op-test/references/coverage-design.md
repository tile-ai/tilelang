# Trustworthy Coverage Design

Read this reference when identifying missing cases or designing boundary, negative, gradient, and stateful tests.

## Use Ten Review Dimensions

Evaluate functionality, accuracy, boundaries, gradients, state mutation, invalid-input rejection, layout and interfaces, backends and branches, randomness, and execution evidence. The first nine dimensions describe what the tests cover; execution evidence indicates whether those cases were actually collected and completed on the specified target.

For each dimension, record `covered`, `partial`, `missing`, `unknown`, or `not_applicable`, cite case IDs, and explain the status. Only trustworthy cases can bring a dimension to `covered`. If the reviewed operator contract shows that gradients, state, or randomness do not apply, do not require those tests artificially.

These dimensions intentionally overlap. One BF16 tail-block case may simultaneously cover functionality, accuracy, boundaries, layout, and a backend path. Still record each dimension separately so that a generic claim of "functional coverage" does not hide missing tail-block, gradient, or state checks.

## Build a Contract Matrix

Starting from the requirements, map existing trustworthy assertions to them item by item. The matrix may use these dimensions:

- Public inputs/outputs, dtype, rank, and shape.
- Optional parameters and their dependencies.
- Layout, stride, aliasing relationships, and contiguity.
- Normal, zero/empty, minimum/maximum, and numerical-range behavior.
- Host dispatch, backend, JIT specialization, and kernel algorithm paths.
- Outputs, auxiliary outputs, gradients, and state mutation.

Coverage cannot be calculated from the number of test functions. Parameterized cases, values generated by helper functions, skip conditions, and backend selection collectively determine what actually executes. Report inapplicable requirements separately from missing and unknown requirements.

## Separate Test Levels from Test Categories

First check whether the current repository actually defines test levels and how they are selected. If it does not, distinguish targeted regression, complete relevant testing, and extended testing with explicit file or nodeid lists; do not introduce environment variables without implementation support.

Negative and boundary are test categories. Critical boundaries should be included in routine regression lists. Do not assume that different test sets necessarily contain one another progressively; verify the cases actually collected and their coverage relationships.

## Tail-Block and Alignment Cases

For a candidate block size `B`, values near `B` are often highly discriminating:

```text
B-1, B, B+1, 2B-1, 2B, 2B+1
```

Use only values supported by the public contract and large enough to expose path differences, and record:

1. The logical dimension and final runtime size.
2. The source of `B` on the current dispatch path.
3. Whether the case produces a remainder (`size % B != 0`).
4. An independent expected result and complete assertions.
5. The defect that the case is intended to detect.

Distinguish these different kinds of tail blocks:

- Data-tile tails inside the kernel.
- Task-to-core distribution tails when the workload is not divisible by the core count.
- Vector or DMA alignment tails.
- Grouped or persistent-loop tails.
- Physical padding around a logical Tensor.

The same case may trigger only one kind of tail block. If static analysis cannot prove the actual path, mark it `PATH_UNKNOWN` until runtime evidence is obtained.

## Constraint-Aware Parameter Combinations

List parameter dependencies before combining parameters. Generate valid positive cases from the constraints; create negative cases only when the documentation explicitly requires rejection. At lower test levels, prefer pairwise or path-oriented combinations. Use Cartesian products only when justified by the risk and execution cost.

Before adding a large matrix, estimate the number of compilation variants, Tensor memory, reference memory, worker concurrency, and execution time. One case may cover multiple compatible requirements, but its purpose must be stated clearly.

## Specialized Assertions

### Quantized and Random Operators

According to the operator requirements, validate quantized data, scale factors, layout/packing, unused data channels, truncation counters, and bias/distribution properties. Even if numerical data uses another acceptance criterion, layout metadata may still be suitable for exact comparison.

### Gradient Operators

Compare every required gradient with a reference that supports autograd, and add a small mathematical check when feasible. Do not assume that a custom BF16 kernel supports double-precision `gradcheck`.

### Stateful or In-Place Operators

Clone the DUT and reference inputs separately. Compare expected state changes and, when required by the contract, verify that source Tensors, adjacent storage, padding, or unselected rows remain unchanged.

### Negative Cases

Use an exact acceptance criterion for exception rejection. An exception caused by a missing dependency, compilation failure, device configuration, OOM, or another unrelated reason does not satisfy a negative-test requirement.
